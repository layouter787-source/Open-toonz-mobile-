# Android tablet port — dependency matrix

Date: 2026-10-10  
Status: source audit; no Android APK build is claimed.

## Known blockers before removing the Android CMake guard

| Component | What the repository currently does | Android issue | Required port work |
|---|---|---|---|
| Qt Serial Port | The top-level Qt module list now adds `SerialPort` only for non-Android targets. `stopmotionserial.cpp` provides a no-device fallback when `Q_OS_ANDROID` is set; desktop builds retain the original `QSerialPort` implementation. | Qt 5.15 for Android does not support the Qt Serial Port module, so external serial lighting/controllers do not operate in the Android build yet. | Later add and test an Android-compatible USB/serial backend if external stop-motion controllers are required. |
| Qt Print Support | The CMake module list and `print.cpp` are now selected only for non-Android targets. Xsheet PDF export remains in `exportxsheetpdf.cpp` and uses `QPdfWriter` from Qt Gui. | Qt Print Support is unavailable on Android in the documented Qt module set, and the traditional print dialog is a desktop workflow. | Keep Android independent of `QPrinter` / `QPrintDialog`; validate PDF generation separately and use the Android share/save workflow if export is retained. |
| Qt Multimedia Widgets | The top-level Qt module list now adds `MultimediaWidgets` only for non-Android targets; the application target's explicit link to it was already limited to the Apple branch. | Qt 5.15 Android platform notes say Qt Multimedia Widgets is not supported on Android. | Verify the Android source path contains no direct widget-module headers; design a supported camera-preview path before enabling a full stop-motion video view. |
| OpenToonz runtime data (`stuff`) | The Android packaging block stages the original repository `stuff/` tree under the build-tree package's `assets/stuff` and generates a file manifest; `TEnv` contains first-run copying into `QStandardPaths::AppDataLocation`. | Android assets are read-only, and the current native CMake guard stops before package staging executes. The new path has not been built or exercised on a device. | After the link/dependency guard is safely resolved, verify every packaged asset, first-launch copying, app-private permissions, upgrade behavior and startup with a clean install. |
| Main application graphics startup | The Android branch of `main.cpp` now configures `QSurfaceFormat` for OpenGL ES and does not run the desktop GLUT/`QGLFormat` startup block. | This does not port the renderer itself: other OpenToonz rendering and tool code still depends on legacy OpenGL APIs and has not been compiled or tested against the Android GLES stack. | Trace the rendering call graph, replace incompatible desktop-only APIs where needed, and compile/test a native Android ABI before enabling the full target. |
| Offline GL renderer and vector drawing | `tofflinegl.cpp`, `qtofflinegl.cpp` and `qtofflinegl.h` use `QGLPixelBuffer`/`QGLFormat`; the offline renderer and many drawing paths use immediate-mode calls such as `glBegin`/`glVertex`; the Android source has no completed renderer factory path. | These APIs are desktop OpenGL compatibility features and are absent from OpenGL ES. Guarding the `QGLPixelBuffer` include alone is not enough: it would either fail compilation at the remaining GL calls or silently remove raster/vector rendering. | Port the shared drawing primitives and offline renderer to an ES-compatible vertex-buffer/FBO backend, select it in `tofflinegl.cpp`, and test raster/vector rendering on ARM64 Android before enabling the target. |
| Shader effects | `stdfx/shadingcontext.cpp` and related shader files include GLEW and use desktop shader, transform-feedback and immediate-mode functions. | GLEW and OpenGL compatibility functions are not an Android GLES renderer; some transform-feedback operations require different GLES versions/extensions. | Replace the GL loader with Qt/OpenGL ES function wrappers; port shaders and texture/readback formats; implement a GLES-compatible transform-feedback or CPU fallback for affected effects. |
| Desktop OpenGL libraries | `AndroidLegacyGL.cmake` now defines pinned GL4ES, Android GLU tessellation, and a FreeGLUT font adapter; `toonz/CMakeLists.txt` selects those targets in its Android executable link branch. | The isolated compatibility libraries cross-link, but the original editor's entire renderer still has desktop-only APIs and has not been compiled as a whole against GLES. | Integrate the compatibility layer into every renderer/library target, port unsupported rendering operations, and build/test the original editor on ARM64 Android before enabling the target. |
| Android OpenCV package | The CMake hook accepts `OPEN_TOONZ_ANDROID_OPENCV_ROOT` or `OPENCV_ANDROID_SDK_ROOT` and resolves the package at `sdk/native/jni`. A script fetches official OpenCV 4.14.0 Android SDK and verifies its SHA-256 before extraction. | Stop-motion webcam code still uses OpenCV, so the package must match the chosen Android ABI. This does not resolve the other native graphics/dependency blockers. | Keep the version and checksum pinned, pass the SDK root to CMake, and link-test with the Android toolchain. |
| Native image/math dependencies | Desktop branches locate TIFF, PNG, JPEG, GLEW, SuperLU, LZ4, LZO, TurboJPEG, OpenCV, FreeType, MyPaint, USB and related libraries. The Android branch now excludes the legacy MOV/3GP proxy sources that call an external 32-bit helper, and `tiio.cpp` skips QuickTime helper registration on Android while retaining FFmpeg registration when available. | These native libraries cannot be assumed to exist as host-system libraries for an Android NDK target; libraries must be Android/ABI-compatible, and several hardware/codec features may be unavailable. | Classify each library as required/optional, cross-compile required components for the chosen ABI, and conditionally exclude optional desktop/hardware features. Test MOV/3GP only when the packaged FFmpeg build supports the formats. |
| Android pencil-test capture UI | The Android app target selects `penciltestpopup_qt.cpp` and `cameracapturelevelcontrol_qt.cpp`, which use Qt's video-surface API instead of the OpenCV-based desktop pencil-test implementation. The source now requests `android.permission.CAMERA` at runtime when the user selects a camera and links Qt Android Extras for this purpose. The stop-motion webcam subsystem remains OpenCV-backed. | Camera permissions, Qt Multimedia's Android backend, and the camera pipeline still require physical-device validation. | Test denied/granted permission paths, camera capture and frame saving on a tablet; keep desktop 64-bit capture sources unchanged. |
| Main executable linking | `toonz/sources/toonz/CMakeLists.txt` now has a `BUILD_ENV_ANDROID` branch linking the original `OpenToonz` executable to Qt Android Extras, the graphics compatibility targets and the original engine libraries. The Android default build excludes LZO CLI helpers and desktop helper executables from the default build. | This is only a first-pass link list: required native libraries such as TIFF/PNG/JPEG/LZ4/SuperLU/MyPaint/OpenCV and their transitive dependencies have not all been proven to be built for the selected Android ABI; the complete engine has not been linked. Helper-process-dependent features remain unavailable. | Define and cross-build the complete ABI-matched dependency graph, audit every library target's transitive links and compile definitions, then run a real Android configure/build before weakening the top-level guard. |
| Qt Android packaging | The Qt 5.15 Android manifest template preserves `androiddeployqt` placeholders, sets `com.toonz.tab` / `ToonzTab`, requests landscape, requires touch hardware and excludes small/normal screen classes. The app CMake stages the original `stuff/` assets and declares the original native executable. | The top-level fail-fast guard prevents configure/package staging by default, and the native dependency graph is not complete. No successful full-editor APK exists. | Finish and validate ABI-matched native dependencies and renderer paths, then build the actual original app, package with `androiddeployqt`, and verify it on a physical tablet. |

## New graphics cross-build work (2026-10-10)

- `toonz/sources/cmake/AndroidLegacyGL.cmake` pins GL4ES and the Android GLU port to immutable commits and configures static ARM64-compatible targets. GLU is compiled in C++14 mode because this legacy Mesa code still uses the removed C++17 `register` specifier; the rest of OpenToonz remains C++17.
- `ci/android/graphics-probe/` and `.github/workflows/android-native-graphics.yml` cross-compile and link a small NDK executable referencing fixed-function OpenGL and GLU tessellator symbols. This is a graphics dependency probe, **not** the original editor build and **not** an APK.
- The compatibility library targets are referenced by the original `OpenToonz` executable's Android link branch, but the full renderer/library graph is not yet validated as a coherent GLES implementation. Do not remove the top-level Android fail-fast guard until the complete native dependency/link path builds successfully.

The isolated Android graphics probe now passes on GitHub Actions for `arm64-v8a`: GL4ES, Android GLU, and the custom FreeGLUT font adapter (stroke and bitmap fonts) compile and link against the NDK. The Qt-owned EGL callback setup is also cross-linked. See [the passing graphics workflow](https://github.com/layouter787-source/Open-toonz-mobile-/actions/runs/38082427304). This test does not compile `OpenToonz`, exercise the GL context on a device, or produce an APK; the native application CMake guard remains in place.

## Safe completion rule

The Android executable and first-pass link branch exist, but their presence does not prove that all linked engine libraries or renderer operations are Android-compatible. Do not remove the top-level fail-fast guard simply to make CMake proceed. Remove it only when unsupported module references are gated/replaced, every required native library is built for the chosen Android ABI, the renderer and shader paths compile against the supported GLES backend, and a real Android toolchain configures and links the original application target.
